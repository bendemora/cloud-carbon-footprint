Cached estimates can be estimated again (points 2 and 3 of ADR 0025). cli: add the `refresh-estimates` command (`yarn workspace @cloud-carbon-footprint/cli refresh-estimates --startDate 2026-11-01 --endDate 2026-11-07`, with `--groupBy`, `--all` and `--cloudProviderToSeed`). It estimates the cached periods of a date range that hold provisional rows again from billing data, with one request for each run of adjacent periods, and replaces them in the estimates cache. With `--all` it takes every cached period in the range, which also picks up billing data that arrived late. It never fills gaps. For each period it replaces the rows of the cloud providers that the new estimate has rows for, and leaves the period alone when the new estimate is empty. It keeps the cached rows of a provider when the new ones have a worse quality tier in some region, which happens when a grid intensity source cannot be reached during the run. A run that fails is reported and the others go ahead; the command then ends with exit code 1. The `grid-intensity-doctor` command now also prints how many periods the estimates cache holds for each grouping and how many of them are provisional. app: add `App.refreshEstimates`, `App.getCachedPeriodCounts` and `App.getCostAndEstimatesWithoutCache`, and a `cachedEstimates` option on `App.getGridIntensityCapabilities`. Each cache manager gains `replaceEstimates`, `getCachedPeriods` and `locationOf`. The local cache file is now written to a temporary file and renamed, so a write that fails part way leaves the file as it was; the directory of the cache file must be writable for that. With `CACHE_MODE=GCS`, a date that is already among the cached results is no longer written twice. Requests to `GET /footprint` never start a refresh, and estimates are unchanged. api: `GET /api/grid-intensity/capabilities` adds `cachedEstimates`, the counts the doctor prints, when the request carries `cachedEstimates=true`. Not built: the second mode of the refresh, which re-prices rows from their stored fields. Not run: the MongoDB replace against a real server, the Google Cloud Storage replace against a real bucket, and a refresh against a cloud provider's billing data.
