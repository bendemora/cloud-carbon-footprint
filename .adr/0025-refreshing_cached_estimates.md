# 25. Refreshing cached estimates whose grid intensity can improve

Date: 2026-11-10

## Status

Accepted with the merge of pull request #32, which builds the marker (point 1 of the decision). Design section 12 put the marker before the first live source. Replace and refresh (points 2 and 3) are built too, in pull request #34, except the second mode of the refresh, which re-prices rows from their stored fields. The implementation notes at the end record what was built.

## Decision

A cached period can be estimated again when its grid intensity was not the best the configuration can deliver. Three additions make that possible.

1. **A marker.** `Provenance` gains an optional `isProvisional` flag. The resolver sets it when the same configuration could give a better result later:
   - the period was only partly covered (data not published yet, a gap, or a period that runs beyond the latest data);
   - the source reports its points as preliminary (a forecast, or an estimate it will replace), through a new optional flag on `IntensityPoint`;
   - a source that is configured, acknowledged and mapped for the region was unavailable (a failed request or probe) and a lower-ranked source answered instead.

   A result is final when the best eligible source served the whole period with settled data, and also when only the static table can serve the region. The quality tier is unchanged by the marker.

2. **Replace.** Each cache manager gains an operation that replaces the cached rows of given periods and providers. `LOCAL` and `GCS` rewrite the cache file with the new periods in place of the old. `MONGODB` deletes the rows of those periods and providers, then inserts the new ones.
3. **Refresh.** `packages/app` gains a refresh operation that estimates cached periods in a date range again from billing data and replaces them, by default only the periods that hold provisional rows. It is a CLI command, and `export-dataset` (design section 11.2) runs it for the range it is about to write. Requests to `GET /footprint` never start it. The doctor command and the capabilities endpoint report how many cached periods are provisional.

Design section 6.2 stands: a source failure never aborts an estimation run. The fallback rows are cached with their real tier and the marker.

Once rows carry the fields of ADR 0024, the refresh gains a second mode that re-prices a row from its stored operational energy and embodied emissions, without reading billing data. It is meant for long histories, for example after a source is added.

## Context

Verified in the code on 2026-11-10 (trunk `a42b5ac6`):

- The `@cache()` decorator (`packages/app/src/Cache.ts`) asks the cache manager which dates of a request are missing and estimates only those. A date counts as cached when any result exists for it (`getMissingDates` in `packages/app/src/common/helpers.ts`, and its MongoDB equivalent in `MongoDbCacheManager.ts`). What the rows contain is not looked at.
- `ignoreCache=true` returns new estimates and does not write them to the cache.
- No cache manager can replace a period today. `LocalCacheManager` merges new results over cached ones for the same timestamp, but it is only ever given missing dates. `GoogleCloudCacheManager.setEstimates` appends the new results to the cached ones, and `MongoDbCacheManager.setEstimates` inserts rows, so writing a date twice would duplicate it in both.
- The tests of the decorator's missing-dates behaviour have been skipped upstream since 2022 (`describe.skip('populates missing dates')` in `packages/app/src/__tests__/Cache.test.ts`).
- Provenance says how good a row's intensity is (`qualityTier`, `isEstimated`), not whether it could be better later.

Why this needs deciding now:

- The resolver falls back when a source fails (design section 6.2) and estimates from partial data when a period is not fully published (the implementation notes under 6.2). Both are right for the run. With a cache that never looks again, one outage or one early run fixes tier C or D rows for good. It applies to every live source, starting with the first one in Phase 2. The Electricity Maps lookup the fork inherited avoided it only by stopping the run, and ADR 0026 has since removed that lookup.
- The same holds when the configuration improves. Adding a source, a credential or a licence acknowledgement does not touch periods that are already cached.
- How soon each open source publishes settled values is not verified yet (design section 14).

Alternatives considered:

- Stop the run when a source fails, as the Electricity Maps lookup did until ADR 0026 removed it. It protects the cache from failures only, gives up the availability rule in section 6.2, and does nothing for late data or a changed configuration.
- Do not cache a period that holds provisional rows. Every request would then read the billing data for those periods again. While a failure is remembered for the capability TTL (24 hours by default), each of those reads would end in the same fallback.
- Refresh on read, inside the decorator. A read would become slow and costly at times the caller cannot predict, because billing queries cost money on Athena and BigQuery. It can be added behind a setting once the explicit refresh has proved itself.
- Cache energy only and apply the intensity when rows are read. It removes the problem at its root, but it changes every reader of the cache, the MongoDB paging and the cost of a read, which is more than this programme should take on. Re-pricing from stored fields gets most of the benefit.

## Consequences

- `Provenance` and `IntensityPoint` each gain one optional flag. Rows cached before the marker count as final, so nothing is refreshed unless a date range is asked for with the option to include every period.
- The cache managers gain one operation each. The MongoDB replace is a delete followed by an insert, not a transaction: if it fails between the two, the period is missing from the cache and the next request estimates it again. The GCS manager stops appending without looking for the date. The local replace writes through a temporary file and a rename, which also closes the partial-write fault noted in PR #15.
- The skipped decorator tests are replaced by tests that run, covering missing dates and the replace path.
- A refresh costs one billing request per provider and run of adjacent periods, as seeding the cache does. Refreshing recent periods also picks up billing data that arrived late, which the cache never did before. That is a side effect, not a goal.
- An operator who never runs the refresh keeps provisional rows. They are labelled in the API and the export, and the doctor reports their number, so the gap is visible.
- Re-pricing, once ADR 0024 is in place, is exact for known usage. It is approximate for unknown-usage rows on AWS and Azure, whose inherited embodied share was priced at the first intensity. A refresh from billing data is exact for both.
- Hourly grouping (Phase 3) multiplies the number of periods. The refresh works on date ranges, so its shape does not change, but finding provisional periods in MongoDB then needs an index.

## Implementation notes

### The marker (2026-11-12)

- `Provenance.isProvisional` is `true` on a provisional result and absent otherwise. A final row and a row estimated before the marker existed therefore look the same, which is what the consequences above ask for.
- The resolver decides it from the sources it tried for the usage period (`mayServeMore` in `GridIntensityResolver.ts`). A source could serve more later when its settled points do not cover the whole period and the part that is missing is one it can be asked for: not published yet, a gap, still preliminary, or not fetched because a request failed. A result is provisional when that is true of any source tried for the period. The search stops at the first source that covers the whole period, so sources after that one are not tried and do not count. When no source covers it, every source was tried and all of them count.
- What a source can be asked for starts at the first whole period, of the granularity the resolver asks it for, that begins at or after the start of its data (`earliest`). A usage period that lies before that will never be served by the source and is final on its account. Four cases follow that the decision does not spell out. A period that lies wholly before the start of a source's data is final. A period that starts before a source's data and is covered from there on is partly covered, estimated and tier C, but final. A day of usage asked for by the day is final when the source's data starts at noon that day, although the source has hours of it: the resolver does not ask by the hour for it. A source that is failing but already holds the whole period in the store gives a final result, and so does a failing source whose data starts after the period.
- Two cases cannot be judged, and the result is provisional. After a failed capability probe in a new process the source's window is not known. After a failed store read, points the store holds were not seen, so a fallback may be worse than the same configuration gives when the store works.
- One case is provisional that the three bullets of point 1 do not name: a lower-ranked source covers the period while a higher-ranked one has only part of it, or nothing yet, without having failed. The decision's definition of a final result ("the best eligible source served the whole period with settled data") covers it.
- A gap in a source's history that never fills leaves its periods provisional for good, as point 1 accepts ("a gap"). A refresh will estimate them again each time it runs. The same holds for a source whose data ends in the past, a loaded file for example: every later period stays provisional while that source is configured. A source that declares no `earliest` keeps every period it has no data for provisional too.
- `IntensityPoint.isPreliminary` is the source's flag for a value it will replace. The resolver uses a preliminary point and marks the result. It holds the point in memory, in the store it already keeps for sources with session retention, so a run does not ask for it again. It never writes one to the configured store, so a later run fetches the period again. A preliminary point never takes the place of a settled one for the same period. This settles the question the NESO spike raised in its section 4.6: a stored preliminary point would never have been fetched again.
- Held points are released together, by the first resolve call after the capability TTL, and a new process starts with none. If the source cannot be reached then, the result has less than before: in a test of 2026-11-12 a day that had 24 points, two of them preliminary, came back with 22 and tier C. For the refresh of point 3 this means that a refresh run during an outage can give a row that is worse than the one it replaces. The row stays provisional in that case, except when the source's lookback has moved past the period. The refresh keeps the cached rows in that case: see "A refresh never puts worse rows in the place of better ones" below.
- When no source can serve a region and the adapter falls back to the provider's static table, the fallback row is provisional if a configured source could serve the period later (`NoIntensityAvailableError.mayImprove`).
- `mergeProvenance` marks a merged row provisional when either part is. Rows that differ only in the marker are not marked estimated because of it.
- The quality tier is not changed by the marker.
- Not handled, and not reachable until usage is resolved by the hour (Phase 3): after a failed probe in a new process the resolver reads the store at each granularity, finest first, and a stored daily value that covers an hour of usage gives a final tier B result where a healthy run would give tier A.
- Tests: `packages/grid-intensity/src/__tests__/provisional.test.ts` covers the resolver and the adapter for each case above, and `packages/core/src/__tests__/provenance.test.ts` covers `mergeProvenance`.

### Replace and refresh (2026-11-12)

What was built:

- **Replace.** `CacheManager.replaceEstimates(estimates, grouping, cloudProviders?)`. For each period in the estimates it removes the cached rows of the given cloud providers and puts the rows of the estimates in their place. Providers are compared without regard to case. With no providers it replaces every row of those periods. A period that is not cached is added, and periods that are not in the estimates are left alone. `setEstimates` logs a warning when it fails and carries on. Replace fails, so that its caller knows the rows were not replaced.
- `LOCAL` reads the cache file as a stream, writes the new file in pieces of about 16 MiB to a temporary file in the same directory, and renames that file over the cache file. `setEstimates` writes the same way now. A write that fails part way leaves the cache file as it was and removes the temporary file. This closes the partial-write fault noted in PR #15.
- `GCS` reads the object, uploads the new one and waits for the upload to end. `setEstimates` still writes the cached results it holds and then the new ones, but it looks for the date first: a date that is among both is written once, with the new result.
- `MONGODB` deletes the rows of the periods and providers with one `deleteMany`, then inserts the new rows with one `insertMany`. It is not a transaction, as decided.
- **A list of what is cached.** `CacheManager.getCachedPeriods(grouping, range?)` gives the timestamp of each cached period, whether any of its rows is provisional, and the worst quality tier of its rows for each cloud provider and region. It is a second new operation on each manager, which the decision does not name. The refresh and the count below have to see what is cached without changing it, and the reads that the `@cache()` decorator uses create the cache file, object or collection when it is missing. `MONGODB` answers with one aggregation over the rows of the collection. A third small operation, `locationOf(grouping)`, names the file, object or collection for the command's output.
- **Refresh.** `App.refreshEstimates(request)`, in `packages/app/src/RefreshEstimates.ts`. It lists the cached periods of the grouping whose timestamp lies in the date range, takes the provisional ones, or all of them with `includeFinal`, groups them into runs of adjacent periods and estimates each run with one request, one run after the other. The estimation that `@cache()` wraps is now a method of its own, `App.getCostAndEstimatesWithoutCache`, which the cached method and the refresh both call. The refresh returns a summary: the cached periods in the range, how many were provisional before and are afterwards, the runs, and how many periods were refreshed, left alone, kept, or not refreshed because their run failed.
- **The command.** `yarn workspace @cloud-carbon-footprint/cli refresh-estimates --startDate <date> --endDate <date>`, with `--groupBy` (`day` unless given), `--all` for every cached period and `--cloudProviderToSeed`. It prints the summary and ends with exit code 1 when a run failed. It closes the connection of the estimates cache and the grid intensity store, as the other commands do.
- **The count.** `App.getCachedPeriodCounts()` gives, for each grouping the cache holds periods of, the number of cached periods and how many of them are provisional. The doctor prints it under its table, and `GET /api/grid-intensity/capabilities` can add it as `cachedEstimates`.
- **Tests.** The decorator tests that were skipped run again. They cover what the decorator does with missing dates, and that a read never estimates a cached period again or replaces it. Replace and the list on each manager, the refresh, the command, the count and the endpoint parameter have tests of their own. Some of them work on real cache files in a temporary directory.

Where it departs from the decision, or adds to it:

- **Only the rows of providers that answered are replaced.** For each period the refresh replaces the cached rows of the cloud providers that the new estimate has rows for. Rows of a provider that the new estimate has nothing for stay. Otherwise a provider whose credentials are no longer configured would lose its rows.
- **An empty estimate replaces nothing.** A period that the new estimate has no rows for is left as it is, and counted. An estimate comes back empty, without an error, when no provider is configured, and that must not empty the cache.
- **A refresh never puts worse rows in the place of better ones.** When a source cannot be reached, the resolver falls back to a lower-ranked source or to the static factors (design section 6.2). A refresh that runs during such an outage would put tier D rows where tier B or C rows were. The new rows would be provisional, so a later refresh would repair them. Until then the cache, and everything read from it, would be worse than before the refresh. Where the lookback of the source has moved past the period by then, the worse row would be final and no refresh would bring the better one back. So before it replaces the rows of a cloud provider for a period, the refresh compares the cached rows and the new rows of that provider, region by region. For each region that has rows with provenance on both sides, it takes the worst quality tier among the cached rows and the worst among the new rows. If the new one is worse in any region, the cached rows of that provider stay for that period. Other providers of the same period are judged on their own. Rows without provenance stand in the way of nothing: a region that has provenance on one side only is not compared. The summary counts such periods as `keptBecauseWorse`, each once, and the command prints the count with a note that a grid intensity source may have been out of reach. A kept period does not count as refreshed. An operator who wants the worse rows on purpose, after removing a source for example, deletes those periods from the cache, or the whole cache, and estimates again.
- **A failed run does not stop the refresh.** A run whose estimation fails leaves the cache as it was for that run. The other runs go ahead, and the summary names the failed run with its dates and the error message. The same holds when the rows of a run cannot be replaced. The refresh as a whole fails only when the cache cannot be read.
- **The range is a range of period starts.** A period is in the range when its timestamp is, both ends included. A refresh never fills a gap: a period that is not cached is not estimated, and a result for it in a new estimate is dropped.
- **A run ends where its last period ends.** For weeks that is the end of the ISO week, a Sunday, because week periods start on Mondays. The decorator ends its requests for missing weeks on the Saturday (see the last list below). A week that the refresh estimates again can therefore hold a day that the decorator's request for it did not ask for.
- **The endpoint gives the count only on request.** Counting reads the whole cache, and the endpoint is cheap otherwise. `cachedEstimates` is in the response only when the request carries `cachedEstimates=true`, and such a request fails with HTTP 500 when the cache cannot be read. The doctor always counts. When it cannot read the cache it still prints its table and says why under it. With `CACHE_MODE=MONGODB` the doctor now connects to MongoDB for the count.
- **What counts as cached.** A grouping is listed when the cache holds at least one period of it. A cache file that was created and holds nothing is not listed. With `LOCAL` and `GCS` a period that was cached with no rows is a cached period. `MONGODB` stores rows only, so it has no such periods.
- **Replace and the list read the cache strictly.** The decorator's reads treat a cache that cannot be parsed as empty. Replace and the list fail instead, because a replace that went on from there would write a cache without the periods it could not read. They accept one oddity. A cache file is created holding `[]` on one line, which is read as one entry, and the first write to a `LOCAL` cache file keeps that entry as its last line. Replace and the list leave it out.
- **Writing through a temporary file has consequences.** The directory of the cache file must be writable, where before only the file had to be. A cache file that is itself a mount point, a single file mounted into a container for example, cannot be renamed over. A process that is stopped during a write leaves the temporary file behind, and nothing removes it. These three are inferred from how a rename works and were not tried. Two things that a plain rename would lose are kept, and tests on real files cover both: the new file gets the mode of the file it replaces, and when the cache file is a symbolic link the file it leads to is replaced and the link stays. Without that, a write gave a cache file of mode 600 the mode that new files get, 644 where it was tried, and put a regular file where the link was. The same tests showed both before the code was changed. The owner of the file is not kept: the new file belongs to the user the process runs as, which is inferred as well. The name of the temporary file ends in `.tmp.json`, so that the ignore patterns for the cache files of `packages/api` and `packages/cli` cover it too, which `git check-ignore` confirms. A cache file that the process may not write is still left alone: replace and `setEstimates` check that first, as writing in place did by failing.

Not built, or not verified:

- Re-pricing a row from its stored operational energy and embodied emissions, the second mode of the refresh, is not built.
- `export-dataset` does not exist yet, so only the command runs the refresh.
- The MongoDB replace and list ran against a fake driver only. Cases for them are in `MongoDbCacheManager.live.test.ts`, but no MongoDB server was at hand when they were written, so they have not run. No index serves the list. The consequences above still expect one to be needed with hourly grouping.
- The GCS replace ran against a mocked bucket only. That a failed upload leaves the old object in place rests on what Cloud Storage documents.
- No refresh has run against a provider's billing data. In the tests the estimation is replaced. The command was run with the default configuration, which has no provider to ask, with no cache and with a cache file made by hand. With the file it found the provisional periods, asked for two runs, got empty estimates and left the file as it was.

The context above was checked against the code again on 2026-11-12. Two of its statements are not exact, and two faults came to light. This change leaves all four as they are:

- "`ignoreCache=true` returns new estimates and does not write them to the cache" holds as stated for `MONGODB` only. With `LOCAL`, and by the same code with `GCS`, the cache is still read to find the missing dates, and only those are estimated and returned. Run with `LOCAL`, a request with `ignoreCache=true` for dates that were all cached estimated nothing and returned nothing.
- "`GoogleCloudCacheManager.setEstimates` appends the new results to the cached ones": it appended them to the cached results of the request's date range and wrote that as the whole object. Cached periods outside the date range of a request are therefore dropped from the object by every write. Run against a mocked bucket, an object that held two days of January and one of February held two days of February after a request for those two days. This change stops the date from being written twice and leaves the rest.
- The `LOCAL` and `GCS` managers keep the estimates of the last request that estimated something (`fetchedEstimates`), and `getEstimates` adds them to every later answer of the same process. Run with `LOCAL`, the same request made twice returned every period twice the second time. `GCS` has the same code and was not run. It follows, and was not run either, that an API server on one of these two caches repeats periods in its answers once it has estimated anything, until it is restarted, and that it goes on serving the old rows of a period next to the rows a refresh has put in their place.
- The decorator ends its request for a run of missing weeks with moment's `endOf('week')`, a Saturday, while week periods start on Mondays. The Sunday that ends the last week of each run is not asked for. The decorator tests now state this.
